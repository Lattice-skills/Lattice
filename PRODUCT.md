# Lattice — Product

A skills framework for AI engineers who code with AI. Lattice teaches any agentskills.io-compatible agent how to build frontends that match what the user actually wanted — not the default "AI purple-neon-glow" output.

This document captures every product decision: what Lattice is, who it's for, why it exists, and the user experience. For *how* it is built, see [ARCHITECTURE.md](./ARCHITECTURE.md).

---

## 1. What is Lattice?

Lattice is a single installable package containing one orchestrator skill and seven sub-skills, in the [agentskills.io](https://agentskills.io) open format. It works in Claude Code, Cursor, Codex, Copilot, Gemini, opencode, Zed, and any other agent that supports the standard.

A user installs Lattice with one command:

```bash
npx skills add <owner>/lattice
```

Then, in any frontend project, the user invokes the workflow by name:

> *"Use Lattice to design a landing page for my app."*

The agent runs an 8-phase workflow — grill, gather references, build, iterate, extract, enforce — and produces a frontend that matches the user's references, with a generated `DESIGN.md` file that keeps the project consistent forever.

---

## 2. Who is it for?

**AI engineers** — developers who use AI coding agents (Claude Code, Cursor, opencode, etc.) to build products, and who have been frustrated by the gap between "the AI just generated a frontend" and "the AI generated the frontend I wanted."

The user is technical. They know React (or Vue, or Svelte, or whatever stack they use). They know what a design system is. They have strong opinions about their product. They have tried other frontend skills and found them lacking.

**Lattice is not for:**
- Designers using Figma as their primary tool (use Figma + a Stitch export instead).
- Non-technical users who want AI to "just make it look good" (Lattice requires the user to engage — to answer grill questions, to provide references, to mark specific feedback).
- Teams that need a fully-spec'd design system up front (Lattice builds the design system *after* the design is approved, by extracting it from the iteration history).

---

## 3. The Problem We Solve

Frontends generated by AI agents, on first attempt, consistently fail in five ways:

1. **Generic aesthetic** — dark mode with blue/purple/neon gradients, glow effects, no matter what the product is.
2. **Inconsistent UI** — inline CSS, components re-built instead of extracted, no design tokens, no global variables.
3. **No audience modeling** — the agent has no idea who the product is for, so it makes taste decisions that fit "everyone," which means "no one."
4. **Built with perfection, not for the user** — the AI optimizes for code cleanliness rather than what the user actually wanted.
5. **Hallucinated libraries** — the agent invents components and libraries that don't exist.

The user has tried to solve this by:
- Writing longer prompts.
- Telling the AI "make it look like Anthropic" or "make it look like Stripe."
- Feeding 12 screenshots of inspiration.
- Iterating 3–4 times with specific feedback.

**That last workflow works.** Lattice encodes it.

- `redesign-existing-projects` (leonxlnx) — 94K installs
- `minimalist-ui` (leonxlnx) — 88K installs
- `extract-design-system` (arvindrk) — 122K installs
- `shadcn` — 177K installs
- `sleek-design-mobile-apps` (sleekdotdesign) — 182K installs

Most of these skills are **static rules**: "don't do purple-neon," "use design tokens," "extract components." They improve a default output. They do not reach OpenAI/Stripe/Notion/Anthropic quality.

Lattice's differentiator is the **multimodal screenshot + grill + 3–4-iteration loop**, encoded as a single coordinated workflow with explicit handoffs between phases:

1. The agent grills the user to understand the product, the audience, and the vibe.
2. The agent finds and analyzes reference screenshots (multimodal).
3. The agent builds a v1, and runs the user through 3–4 cycles of specific feedback.
4. The agent extracts a `DESIGN.md` from the approved design.
5. The agent enforces the design system forever.

No existing skill does this end-to-end. Lattice does.

## 5. The User Experience — the Lattice journey

A user installs Lattice and starts a new project. Here's what happens:

### Step 1 — Invoke
> User: "Use Lattice to design a landing page for a developer tool I'm building. It's called Stave. It's a database client for teams that hate phpMyAdmin."

The agent loads the orchestrator and confirms the workflow.

### Step 2 — Product Grill
> Agent: "Tell me about Stave in one sentence."
> User: "A modern database client for teams that find existing tools ugly or slow."
> Agent: "Who is the primary user?"
> User: "Backend engineers, 25–40, at series A–C startups. They've used DataGrip, TablePlus, Beekeeper. They want something that feels like Linear or Vercel."
> Agent: "Top 1–3 things users do?"
> User: "Connect to a database, browse tables, write and run a query."
> Agent: "Brand vibe — 3–5 adjectives."
> User: "Focused. Dense but not crowded. Restrained color. Confident typography. Like Linear, not like Stripe's marketing site."
> Agent: "What is Stave NOT?"
> User: "Not enterprise-y. Not cutesy. Not friendly. Not consumer."

The agent writes a `brief.md`. The user confirms or amends.

### Step 3 — Direction Selection
> Agent: "Based on your brief, here are 3 directions to consider:
>   1. **Dense dev tool** — Linear, Vercel, Datadog style. Information-first, dark by default, restrained color.
>   2. **Editorial product page** — Stripe, Cron, Posthog style. Big typography, generous whitespace, hero-focused.
>   3. **Hybrid: dense product with editorial hero** — Vercel's marketing site is dense but the homepage has editorial weight.
>
> I'd recommend **#1** because your brief says 'focused, dense but not crowded,' and your Linear reference suggests you want information density. But the hero could borrow from #2 if you want a stronger first impression.
>
> Pick: as-is, with tweaks, or hybrid?"

The user picks. The agent records the choice in `brief.md`.

### Step 4 — Screenshot Collection & Analysis
> Agent: "Drop 5–10 screenshots in `.lattice/references/`:
>   - 3–5 of overall layouts in the chosen direction
>   - 2–3 of specific components (hero, nav, table, button, form)
>   - 1–2 from different angles (mobile, dark mode)
>   - 1–2 anti-references — what you do NOT want
>
> Or paste URLs and I'll download them."

The user drops screenshots. The agent analyzes each: color, type, spacing, layout, elevation, motion. The agent writes an `analysis.md`.

### Step 5 — Alignment
> Agent: "Here's what I see in your refs:
>   - **Color:** predominantly dark, near-black backgrounds (#0A0A0A, #111111), single accent color used sparingly (Linear's purple, Vercel's blue). You're using both — your Vercel ref has blue, your Linear ref has purple. Pick one.
>   - **Type:** Inter or Geist for everything. Tight letter-spacing. Bold for emphasis, regular for body. Your brief says 'confident typography' — I'd go with Inter Display for headlines.
>   - **Spacing:** 4px base scale, generous in marketing pages, tighter in dashboard views.
>   - **Layout:** 12-column grid, asymmetric hero, sidebar for product UI.
>
> I'm planning this for Stave: dark by default, single accent (your choice — blue or purple), Inter throughout, 4px base scale, 12-column grid.
>
> Confirm or push back."

The user confirms with adjustments: "Blue. Inter Display for headlines. Lighter hero, the marketing page is for new visitors, they need more breathing room than the dashboard."

The agent writes `decisions.md`.

### Step 6 — Build & Iterate
> Agent: "v1 is at `app/page.tsx`. Here's what I built: [summary]. Here's my self-critique: [3 things I'd flag]."

The user reviews. They give specific feedback (or vague feedback, which the agent converts into specific options with recommendations). 3–4 cycles later, the user says:

> User: "This is what I wanted."

### Step 7 — Extract
> Agent: "Extracting DESIGN.md. Tokens inferred from your approved v_n. Validating against the spec."

The agent writes `DESIGN.md` to the project root. The agent also runs:

```bash
npm install @google/design.md
npx @google/design.md export --format tailwind DESIGN.md
```

…and writes a `tailwind.config.ts` from the tokens. The project now has a real, machine-readable design system.

### Step 8 — Consistency
From this point on, every change to the frontend is checked against `DESIGN.md`. The `enforce-design` skill is active. The user (or any agent) cannot introduce an inline color or a new typography style without first adding it to `DESIGN.md`.

The project is consistent. Forever.

## 6. The Output — DESIGN.md

`DESIGN.md` is the artifact Lattice produces. It is **not** a Lattice invention — it is [Google Stitch's open standard](https://github.com/google-labs-code/design.md), Apache 2.0.

`DESIGN.md` is a single markdown file with:

- **YAML front matter** — machine-readable design tokens (colors, typography, spacing, components, etc.).
- **Markdown body** — human-readable design rationale in 8 required sections (Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's & Don'ts).

`DESIGN.md` is:
- **Tool-agnostic.** Claude Code, Cursor, Gemini CLI, Antigravity — any agent can read it.
- **Exportable.** `@google/design.md` CLI converts tokens to Tailwind config, W3C DTCG `tokens.json`, or any other format.
- **Validatable.** The CLI catches WCAG contrast violations, missing required sections, malformed tokens.
- **Version-controllable.** It's a file. It diffs. It PRs.

Lattice's `design-md-extract` skill is opinionated about *how* `DESIGN.md` gets generated (inferred from the iteration history, cross-referenced with the brief and decisions), but the output format is the open standard.

## 7. The Value Proposition

**For the AI engineer:** the agent's first attempt looks like the third attempt. You get to "this is what I wanted" in 3–4 cycles, not 12. The output has a real design system, not just code that looks OK.

**For the project:** consistency forever. Once `DESIGN.md` exists, every subsequent change has to respect it. The design system doesn't rot.

**For the user/PM/founder:** the design reflects the audience, not the model's defaults. The product looks like it was built for someone, not for "everyone."

**For the agent ecosystem:** Lattice is a reference implementation of a multi-skill pack with an orchestrator. Other skill authors can learn from the pattern.

## 9. MVP Scope (v1)

Lattice v1 ships with:

- **1 orchestrator** (`lattice`) — the workflow.
- **5 process skills** — `grill`, `references`, `iterate`, `design-md-extract`, `enforce-design`.
- **2 constraint skills** — `anti-default-aesthetic`, `no-inline-styles`.
- **1 starter catalog** — 5 archetypes in `references/catalog/`, as fallback for the agent's web search.

**Cut from v1:**
- `no-hallucinated-libs` — needs a curated library catalog per stack. v1.1.
- `comp-extract-on-second-use` — folded into `enforce-design` for v1. v1.2 standalone.
- **Redesign support** — new build only for v1. v2.

**v1 success looks like:**
- A user can install Lattice, run the workflow on a real product, and ship a frontend they love in under a week.
- The output is a valid `DESIGN.md` that downstream agents can consume.
- 5+ users have shipped with Lattice, with at least 3 public references.

## 11. Naming — why "Lattice"?

A lattice is a structure of points and lines, regular and interlocking. It evokes:

- A **structured framework** — the skills fit together.
- A **grid or scaffold** — the design system that emerges.
- **Mathematical precision** — tokens, scales, ratios.
- An **architectural framing** — a way of building.

It is also a real word, not a tech-jargon coinage. It's memorable, easy to type, easy to say. It works in any language. The single word "Lattice" is the package name, the install command, the brand.

**Collisions checked:**
- Lattice (HR/performance tool, lattice.com) — different domain, no conflict.
- skills.sh — clean. No skill named Lattice.
- npm — no major package conflict in the agent skills space.

## 12. Anti-Goals

Things Lattice explicitly does NOT do:

- **Replace Figma.** Designers using Figma should keep using Figma. Lattice is for engineers building frontends with agents.
- **Generate frontends from a single one-liner.** Lattice requires the user to engage — to answer questions, to provide references, to mark specific feedback. It is not a magic button.
- **Cover every frontend type equally well.** v1 is biased toward marketing/landing pages and SaaS dashboards (the most common AI-engineer use case). Other types are universal via user-supplied screenshots, but the skill content is sharper for these two.
- **Be opinionated about tech stack.** Lattice is tech-agnostic. The user picks (or already has) their stack. Lattice works with whatever they have.
- **Lock users in.** DESIGN.md is an open standard. Lattice's output is portable. If a user uninstalls Lattice, their `DESIGN.md` still works with any other agent.
