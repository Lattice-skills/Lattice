# Lattice — Architecture

A skills framework for AI engineers who code with AI. Lattice teaches any agentskills.io-compatible agent how to build frontends that match what the user actually wanted — not the default "AI purple-neon-glow" output.

This document captures every architectural decision made during the design phase. It is the source of truth for *how* Lattice is built. For *what* Lattice is and *why* it exists, see [PRODUCT.md](./PRODUCT.md).

---

## 1. Mission

Make the agent's first frontend attempt look like the third one. Get a user to "this is what I wanted" in 3–4 cycles, not 12, by encoding a multimodal-screenshot + iteration workflow as installable skills.

---

## 2. The Problem

Frontends generated by AI agents, on first attempt, consistently fail in five ways:

| # | Failure | Root cause |
|---|---------|-----------|
| A | No audience modeling — agent defaults to "AI user" | No context-gathering step in the agent's flow |
| B | Generic aesthetic — dark + blue/purple + neon glow regardless of product | Model training bias; no anti-pattern rule in context |
| C | Inline CSS, components re-built, no design system | No discipline enforcing tokens / extraction |
| D | "Built with perfection" — right patterns, wrong product | Agent optimizes for code cleanliness over user outcome |
| E | Hallucinated libraries / components / APIs | No grounding in the real ecosystem |

Existing skills on skills.sh (frontend-design, web-design-guidelines, impeccable, ui-ux-pro-max, design-taste-frontend, etc.) address *some* of these via static rules. None of them encode the **multimodal screenshot + grill + 3–4-iteration loop** as a coordinated workflow. That is the gap Lattice fills.

---

## 3. Design Principles

1. **Universal by user's screenshots, not by our taxonomy.** Lattice does not enumerate frontend types (marketing, dashboard, mobile, e-commerce). Whatever the user shows, we work on. Scope is supplied by the user as image inputs, not embedded in skill content.
2. **Two modes, not one.** Design phase (high creativity, lots of iteration) and consistency phase (low creativity, high discipline). Different rules are active in each.
3. **Multimodal is a hard requirement.** The screenshot + iteration loop is the differentiator. If the agent cannot see images, Lattice degrades clearly — it does not pretend to work.
4. **The agent recommends, the user decides.** Every iteration step where the user's input is vague produces a recommendation with explicit reasoning. The user can accept, reject, or override. The agent never just asks "what do you want?" without grounding the question.
5. **Standards over invention.** Use existing open standards wherever possible (agentskills.io for the format, Google Stitch DESIGN.md for the design system artifact, W3C DTCG tokens where applicable). Lattice invents nothing that the ecosystem already has.
6. **Single product, multiple skills.** One install. One orchestrator skill that knows the workflow. Sub-skills activate on demand. The user does not have to learn the routing.

---

## 4. Format & Distribution

- **Format:** [agentskills.io](https://agentskills.io) open standard. Folder per skill, `SKILL.md` at root, optional `scripts/`, `references/`, `assets/`. Originally developed by Anthropic, adopted by Claude Code, Cursor, Codex, Copilot, Gemini, opencode, Zed, and most other agents.
- **Distribution:** [skills.sh](https://skills.sh) directory. Install with `npx skills add <owner>/lattice`. Vercel-hosted leaderboard and search.
- **License:** Apache 2.0. Matches the license of Google Stitch's DESIGN.md and the W3C DTCG work. Has the patent grant clause, encouraging forks and commercial use.
- **Progressive disclosure:** The orchestrator's `description` field is loaded at agent startup; the body is loaded only when the user activates the skill; sub-skills load only when the orchestrator points to them. This keeps the context footprint small.

## 5. Skill Architecture

Lattice is one package containing one orchestrator and seven sub-skills. The orchestrator is itself a skill (top-level `SKILL.md`) and its `description` triggers it. Sub-skills are folders under `skills/` with their own `SKILL.md` files.

```
lattice/
├── SKILL.md                          ← Orchestrator (lattice)
├── README.md
├── ARCHITECTURE.md                   ← this file
├── PRODUCT.md
├── LICENSE                           ← Apache 2.0
├── skills/
│   ├── grill/                        ← product brief + alignment interview
│   │   └── SKILL.md
│   ├── references/                   ← web search + multimodal screenshot analysis
│   │   └── SKILL.md
│   ├── iterate/                      ← build v1 + 3–4 iteration cycles
│   │   └── SKILL.md
│   ├── design-md-extract/            ← generate Google Stitch DESIGN.md
│   │   └── SKILL.md
│   ├── enforce-design/               ← consistency mode after DESIGN.md exists
│   │   └── SKILL.md
│   ├── anti-default-aesthetic/       ← constraint: no purple/neon/glow defaults
│   │   └── SKILL.md
│   └── no-inline-styles/             ← constraint: tokens only
│       └── SKILL.md
└── references/
    └── catalog/                      ← 5 starter archetypes as fallback
        ├── README.md
        ├── saas-marketing.md
        ├── dense-dev-tool.md
        ├── warm-consumer.md
        ├── editorial-content.md
        └── dashboard-admin.md
```

### Why an orchestrator, not just a single mega-skill

A single mega-skill that contains the entire workflow would be loaded into context for *every* frontend task, even trivial ones. With the orchestrator pattern:

- The orchestrator is small (~200 lines) and loaded on demand.
- Sub-skills are loaded only when the orchestrator's workflow reaches the relevant phase.
- The agent's context stays lean.
- Sub-skills can be invoked independently by power users who only want one piece (e.g. just `design-md-extract`).

### Sub-skill activation model

The orchestrator's `SKILL.md` body contains a workflow that names each sub-skill at the right moment. The agent loads the sub-skill's `SKILL.md` on demand. This is the same progressive-disclosure model that the agentskills.io standard is built around.

## 6. The Workflow — 8 Phases

The orchestrator runs an 8-phase workflow. The user explicitly invokes the framework ("use Lattice," "let's design with Lattice," etc.) — Lattice does not auto-detect frontend work, because that false-positive risk is too high for a multi-step process.

### Phase 0 — Activate
- **Trigger:** explicit user invocation.
- **Action:** the agent reads the orchestrator's `SKILL.md`, restates the 8-phase workflow to the user, and asks for confirmation to start.
- **Output:** user has confirmed they want the Lattice workflow.

### Phase 1 — Product Grill (`grill` skill)
- **Input:** the user's project and what they want to build.
- **Action:** the `grill` skill interviews the user. Questions are asked one at a time, conversationally. Topics:
  1. What is the product? (one sentence, then expand)
  2. Who is it for? (audience — concrete personas, not "everyone")
  3. What is the top 1–3 things users do? (jobs to be done)
  4. Brand vibe — 3–5 adjectives.
  5. What is this product NOT? (anti-references — what to actively avoid)
  6. Tech stack (Next.js, Vite+React, Svelte, etc.) — implicit from the user's project if it already exists.
- **Output:** `brief.md` at the project root. One file, ~30–60 lines. Re-used as context throughout the rest of the workflow.

### Phase 2 — Direction Selection (`references` skill, part 1)
- **Input:** `brief.md`.
- **Action:** the agent suggests 3–5 starting UI directions. The `references/catalog/` is the *fallback* (5 starter archetypes: SaaS marketing, dense dev tool, warm consumer, editorial content, dashboard admin). The agent first searches the web for sites that match the brief's vibe, audience, and jobs. Only if the search returns no good matches does the agent pull from the catalog. If still nothing, the agent uses its own knowledge of well-designed sites.
- **For each suggested direction, the agent provides:**
  - A short descriptive name ("modern SaaS landing," "editorial product page").
  - 2–3 reference sites the user can look at, with what each does well.
  - The vibe adjectives from `brief.md` mapped to the direction.
- **User picks:** as-is, with tweaks, or hybrid of two directions.
- **Output:** the chosen direction recorded in `brief.md` (a "Direction" section appended).

### Phase 3 — Screenshot Collection & Analysis (`references` skill, part 2)
- **Input:** the chosen direction.
- **Action:** the agent asks the user for screenshots organized in a folder (or saved by the agent if the user prefers). The agent specifies what to collect:
  - 3–5 screenshots of overall layout / composition in the chosen direction.
  - 2–3 screenshots of specific components (hero, nav, card, button, form, table).
  - 1–2 screenshots from different angles (mobile, dark mode, dense view).
  - 1–2 **anti-references** — sites/screenshots the user does NOT want to be like.
- **Multimodal analysis:** the agent reads each image. Extracts and outputs:
  - Color palette (descriptive names + approximate hex)
  - Typography (font families, weight hierarchy, type scale)
  - Spacing & density (generous / tight / very dense, scale rhythm)
  - Layout patterns (grid, asymmetric, centered, split)
  - Elevation / depth (flat, soft shadows, hard shadows, glassmorphism)
  - Motion (if visible in screenshots or referenced sites; static otherwise)
- **Output:** `analysis.md` at the project root. Visual + text analysis. Re-used as context in subsequent phases.

### Phase 4 — Alignment Grill (`grill` skill, part 2)
- **Input:** `brief.md`, `analysis.md`, the chosen direction.
- **Action:** the agent presents its synthesis:
  > "Here's what I see in your references. Here's what I'm planning for your product. Use as-is, or with these tweaks."
- The agent then asks alignment questions, one at a time, focused on the *delta* between references and the user's actual product. E.g.:
  - "Your references are dark-mode-first; should v1 be dark or light?"
  - "References are typographically dense; do you want that density on day one, or start generous and tighten later?"
  - "References lean editorial; your product is a tool — keep editorial vibe, or pull toward utility?"
- Each question offers 2–3 grounded options with a recommendation and explicit reasoning.
- **Loop** until the user says "yes, build it" or "yes, with these adjustments."
- **Output:** a `decisions.md` file capturing the alignment outcomes. Concise, ~20 lines.

### Phase 5 — Build v1 (`iterate` skill, step 1)
- **Input:** `brief.md`, `analysis.md`, `decisions.md`, user's tech stack.
- **Action:** the agent builds v1 in the user's tech stack. The `iterate` skill's rules apply: anti-default-aesthetic is active, but no-inline-styles is *less* aggressive (v1 may have rough edges; the rule tightens in consistency mode).
- **Output:** v1 code. The agent states what it built and a self-critique:
  > "v1 is at <commit/file>. Here's what I'd flag if I were you: [self-critique]."

### Phase 6 — Iterate (`iterate` skill, steps 2–N)
- **Loop structure:**
  ```
  for n in 1, 2, 3, ...:
    1. user provides feedback on v_{n-1}
    2. agent parses feedback for specificity
    3. if specific → build v_n
    4. if vague → ask + recommend (see Iteration Mechanic below)
    5. agent builds v_n, states the diff from v_{n-1}
    6. stop when user says "ship it" OR feedback is vague for 2 consecutive cycles
  ```
- **Feedback format:** mixed text + annotated screenshots. The `iterate` skill enforces this; pure text alone is not accepted.
- **Stop conditions:**
  - **Happy path:** user says "ship it" or "this is what I wanted."
  - **Hesitation path:** user feedback is vague for 2 consecutive cycles. The agent calls it out:
    > "Your last two rounds of feedback have been vague. Either drop a screenshot of what you're imagining, or let's call v_{n-1} done and move to extraction."
  - **Hard cap:** 5 cycles. After 5, the agent suggests extraction even if the user is not satisfied — there are diminishing returns beyond 5.

### Phase 7 — DESIGN.md Extraction (`design-md-extract` skill)
- **Trigger:** user says "this is what I wanted" (or after a soft stop).
- **Action:** the agent generates a [Google Stitch DESIGN.md](https://github.com/google-labs-code/design.md) file at the project root.
  - **YAML front matter:** colors, typography, spacing, rounded, components — all typed per the DESIGN.md spec.
  - **Markdown body sections** in the required order: Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's & Don'ts.
  - The agent validates the file using `@google/design.md` CLI (Apache 2.0, npm-installable):
    ```
    npm install @google/design.md
    npx @google/design.md export --format tailwind DESIGN.md
    ```
- **Output:** `DESIGN.md` at the project root. Source of truth for everything that follows.

### Phase 8 — Consistency Mode (`enforce-design` skill)
- **Activation:** automatic after `DESIGN.md` exists in the project.
- **Behavior:** every subsequent piece of frontend work in the project is checked against `DESIGN.md`:
  - Components must use documented tokens (`{colors.primary}`, `{typography.body-md}`, etc.).
  - No inline styles — tokens only.
  - Token changes require updating `DESIGN.md` first.
  - New components require a `DESIGN.md` entry first.
  - The `no-inline-styles` constraint is now aggressive.
- **Output:** the project stays consistent forever, as long as `enforce-design` is active.

## 7. The Iteration Mechanic (Phase 6 detail)

This is the heart of Lattice. It is what existing skills don't do, and it is what makes the framework valuable.

### Vague vs. specific feedback

**Specific feedback** names an element AND a change AND a desired outcome:
- ✅ "The hero CTA — increase padding-x by 50%, change weight to semibold"
- ✅ "The card grid — change from 3 columns to 2 on tablet"
- ✅ "The headline — color is too cool, push it warmer by ~10%"

**Vague feedback** doesn't:
- ❌ "Make it better"
- ❌ "The hero is off"
- ❌ "Doesn't feel right"
- ❌ "I don't like it"
- ❌ "More polished"

The `iterate` skill maintains a list of vague patterns and triggers the question + recommendation flow on match.

### Question + recommendation flow

When feedback is vague, the agent:

1. **Identifies the dimension(s) the user is gesturing at.** "feels off" = vibe; "too tall" = layout; "too cold" = color; "too busy" = density; "lacks polish" = motion + spacing + typography.

2. **For each dimension, generates 2–3 options** grounded in:
   - The product brief (vibe, audience, anti-references).
   - The references the user provided in Phase 3.
   - The diff between the last two iterations (what already changed).
   - "Best of" picks from the references for each dimension.

3. **For each dimension, picks a recommendation** with explicit reasoning:
   > "I'd recommend **centered hero** because your brief says 'focused, single-action' and your Notion reference uses centered composition. Want to go with that, or try one of the others?"

4. **Always offers the screenshot fallback** as one of the options, not as a last resort:
   > "...or drop a screenshot of what you have in mind — that's the most precise option."

### Specificity escalation

The strictness of the question + recommendation flow escalates over cycles:

- **Cycle 1 of vagueness:** gentle. "I want to be precise here — could you tell me which of these dimensions is the main concern?"
- **Cycle 2 of vagueness:** firmer. "I need a specific change to make real progress. Here are 3 options — pick one, give me a different one, or drop a screenshot."
- **Cycle 3+ of vagueness:** the agent calls it out. "Your feedback has been vague for 2 cycles in a row. Two paths forward: (a) drop a screenshot of what you're imagining, (b) call v_{n-1} done and move to extraction."

The "2 consecutive vague cycles = call it out" rule also serves as a soft stop condition for the iteration loop.

## 8. DESIGN.md Integration

Lattice outputs a Google Stitch DESIGN.md at the end of Phase 7. This is not a Lattice invention — it is an open standard, Apache 2.0, maintained by Google Labs.

### Why DESIGN.md

- **Open standard.** No vendor lock-in. Any agent or tool can consume it.
- **Two-layer format.** YAML front matter (machine-readable tokens) + markdown body (human-readable design rationale). The tokens are normative; the prose provides context.
- **Tooling exists.** `@google/design.md` CLI exports to Tailwind config and to W3C DTCG `tokens.json`. Validation built in.
- **Agent-friendly.** Designed to be consumed by Claude Code, Cursor, Gemini CLI, etc. — the same agents that load Lattice.
- **Adoption signal.** Already in the skills.sh ecosystem (`google-labs-code/stitch-skills`, `design-md`).

### Section order (required by spec)

The agent generates sections in this order, omitting any that don't apply:

1. Overview (also: "Brand & Style")
2. Colors
3. Typography
4. Layout (also: "Layout & Spacing")
5. Elevation & Depth
6. Shapes
7. Components
8. Do's and Don'ts

### Token schema (YAML front matter)

```yaml
version: alpha
name: <project name>
description: <short>
colors:
  primary: <Color>
  secondary: <Color>
  # ... etc
typography:
  <role>: { fontFamily, fontSize, fontWeight, lineHeight, letterSpacing }
spacing:
  <scale-level>: <Dimension | number>
rounded:
  <scale-level>: <Dimension>
components:
  <component-name>:
    <token-name>: <string | {path.to.token} reference>
```

Token references use `{path.to.token}` syntax. Component entries can reference composite values (e.g., `{typography.label-md}`).

### What Lattice adds on top of raw DESIGN.md

Lattice's `design-md-extract` skill does more than just emit the file. It:

- **Infers tokens from the iteration history.** The agent has seen v_1, v_2, v_3, ... — the design has been ratified through feedback. Tokens are extracted from the final approved state, not invented.
- **Cross-references `brief.md` and `decisions.md`.** The Overview section references the brand vibe adjectives and the audience from the brief. The Do's & Don'ts section references the anti-references from the brief and the choices made in alignment.
- **Generates a `tailwind.config.ts` from the tokens** as a side effect, so the user's project can immediately use the design system in code.
- **Validates** the output against the DESIGN.md spec using the CLI.

## 9. The Two-Phase Model (summary)

| | Design phase (Phases 1–6) | Consistency phase (Phases 7–8) |
|---|---|---|
| **Goal** | Get the design right | Keep it right |
| **Mode** | High creativity, lots of iteration | Low creativity, high discipline |
| **Active constraint skills** | `anti-default-aesthetic` | `no-inline-styles` (aggressive) + design system enforcement |
| **Output** | Approved v_n in code | `DESIGN.md` + all subsequent code respects it |
| **User role** | Director (vibe, direction) | Reviewer (consistency) |
| **Stop condition** | User says "ship it" | n/a (runs forever) |

This two-phase split is what existing skills miss. They treat the work as one mode. Lattice recognizes that getting a design right and keeping it right are different problems with different rules.

## 11. Cut from v1 (and why)

Two skills considered for v1 are deferred:

| Skill | Why cut | When to add |
|---|---|---|
| `no-hallucinated-libs` | Requires a verified library catalog per stack (React, Vue, Svelte, etc.). Significant curation work, and stack-dependent. We don't want to ship a half-baked catalog. | v1.1 — start with a React/Next.js catalog, expand per stack as the community contributes |
| `comp-extract-on-second-use` | A code-quality discipline that overlaps with `enforce-design` in consistency mode. Splitting it out is more architecturally clean, but for v1 the rule is folded into `enforce-design`. | v1.2 — split out as a standalone skill once `enforce-design` is mature |

The framework is designed to add these later without restructuring. The 7-skill + orchestrator v1 is the smallest version that captures the differentiator (screenshot + iteration + DESIGN.md).

## 12. Open Questions / Future Work

- **The 5 starter archetypes in `references/catalog/`.** What are the canonical references for each? This is curation work, not architecture.
- **The grill's exact question bank.** The `grill` skill will need 10–20 well-designed questions per phase. These are content, not architecture.
- **The screenshot analysis depth.** How much does the agent extract from each image? How does it handle conflicts between references?
- **The "vague feedback" pattern list.** The `iterate` skill needs a maintained list of vague patterns to detect. This list will grow.
- **Redesign support (v2).** Different workflow: extract current design system → diff vs. desired → migrate component-by-component.
- **Mobile-specific constraints.** Touch targets, gestures, native platform conventions.
- **Enterprise constraints.** SSO flows, accessibility law (WCAG 2.2 AA), design system integration with existing tokens.
- **A web app / docs site.** Not in v1, but a landing page and a workflow walkthrough video will matter for distribution.

## 13. Technical Decisions (locked)

- **Format:** agentskills.io
- **Distribution:** skills.sh via `npx skills add`
- **License:** Apache 2.0
- **Name:** Lattice
- **Repo structure:** one package, orchestrator + sub-skills
- **Standard for design system artifact:** Google Stitch DESIGN.md (alpha)
- **Tooling:** `@google/design.md` CLI for validation and export
- **Output side effect:** `tailwind.config.ts` generated from `DESIGN.md` tokens
